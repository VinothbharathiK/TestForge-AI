TESTFORGE AI — ANTIGRAVITY HANDOFF
Inspection snapshot: 2026-10-29, immediately before the Milestone 4 handoff commit.

1. PROJECT OVERVIEW

TestForge AI is an autonomous API-testing engine. It asks an LLM to create a
pytest suite for supplied FastAPI source, executes the suite in a disposable
Docker runner, classifies the pytest evidence, and repairs eligible generated
test-harness failures.

Intended use: a portfolio project, system-design/interview demonstration, and
potential hackathon submission. The current application is a demo-ready MVP,
not a fully production-secure public service. The service has no user
authentication or rate limiting. Docker reduces the exposure from executing
untrusted code, but is not an absolute security boundary. Do not expose the
service to arbitrary hostile public or multi-tenant workloads without stronger
isolation and operational controls.

2. TECHNOLOGY STACK AND REQUEST FLOW

Frontend: React, Vite, Tailwind CSS, Axios, and lucide-react. Vite's development
server is configured on port 3000; CORS also includes the common Vite port 5173.
The browser API client in frontend/src/services/api.js posts source to
http://localhost:8000/generate-tests and defines the two built-in API presets.

Backend: Python, FastAPI, Pydantic, the OpenAI-compatible AsyncOpenAI SDK,
python-dotenv, the Docker SDK, and pytest. The real model default is Meta Muse
Spark 1.3 at https://api.meta.ai/v1.

Request flow:
1. frontend/src/App.jsx takes the selected or edited route source and calls
   generateAndTestApi() in frontend/src/services/api.js.
2. backend/main.py validates CodePayload and calls
   TestForgeAgent.generate_and_heal() in backend/agent.py.
3. The agent requests a pytest suite from the configured model, validates its
   syntax and shape, and calls ExecutionSandbox.run_test_in_docker().
4. backend/sandbox.py writes main.py and test_app.py in a temporary workspace,
   executes pytest in the isolated runner, captures output, exit code, and
   JUnit counts, then classifies the result from pytest evidence.
5. The agent stops on confirmed API defects, initialization/collection errors,
   and infrastructure errors. It may repair test setup/harness failures up to
   MAX_REPAIR_ATTEMPTS (3); it does not remove meaningful API assertions to
   force a defective application to pass.
6. backend/main.py returns the result. Infrastructure/configuration status
   "error" uses HTTP 503; completed pass, failure, and defect analyses are result
   payloads. frontend/src/utils/resultPresentation.js independently requires
   real passing metrics before rendering a verified pass and requires executed
   assertion evidence before rendering a confirmed defect. App.jsx passes the
   result to AgentLogs.jsx and TestViewer.jsx.

Important functions and modules:
- backend/main.py: configured_cors_origins(), CodePayload, generate_tests().
- backend/agent.py: TestForgeAgent.__init__(), generate_and_heal(),
  _classify_execution_failure(), _repair_prompt(), _validate_pytest(),
  _parse_sandbox_result(), _result(), and aclose().
- backend/sandbox.py: ExecutionSandbox.run_test_in_docker(),
  _run_container_sync(), _classify_pytest_result(), _parse_junit_counts(), and
  _ensure_runner_image().
- frontend/src/utils/resultPresentation.js: isVerifiedPass(),
  isConfirmedDefect(), summarizeResult(), and splitLogEntries().

6. DOCKER AND SECURITY

The implemented runner configuration is in backend/sandbox.py:
- Submitted app source and generated tests execute only in Docker; no host
  execution fallback exists.
- The runner gets one read-only bind mount for the temporary workspace at
  /workspace. The Docker socket and unrelated host filesystem paths are not
  mounted. The container root filesystem is read-only.
- Network is disabled. The container runs as UID/GID 65534, drops all Linux
  capabilities, and sets no-new-privileges.
- Writable /tmp is a 64 MiB tmpfs configured noexec,nosuid,nodev.
- Defaults limit execution to 60 seconds, 512 MiB memory, one CPU quota, 64
  processes, and a Docker local log cap of 4 MiB. Returned pytest output is
  additionally limited to the last 64 KiB.
- Submitted source and generated test UTF-8 sizes are limited to 256 KiB and
  512 KiB. Only a minimal explicit environment is sent to the container:
  PYTHONDONTWRITEBYTECODE, PYTEST_DISABLE_PLUGIN_AUTOLOAD, and TMPDIR.
- The trusted runner image is built from python:3.11-slim and installs pytest,
  FastAPI, pydantic, httpx2, and email-validator. Initial image pull/build and
  package installation need Docker host network access; pytest containers do
  not have network access.
- TemporaryDirectory owns each workspace. The container is created before it
  is started so a startup exception still leaves a handle for finally cleanup.
  Normal execution, timeouts, Docker errors, and executor cancellation have
  cleanup paths; cancellation waits for the executor worker before deleting
  its mounted workspace. Unit tests cover the configuration and cleanup paths.

These are defense-in-depth controls, not proof that Docker is invulnerable.
Docker Desktop, the daemon, kernel, or host can be misconfigured or vulnerable.
The service currently lacks authentication, rate limiting, abuse monitoring,
and multi-tenant isolation. Do not expose it to arbitrary hostile users as a
public execution service. Avoid submitting source that embeds secrets: pytest
tracebacks can include submitted source lines, and result logs are shown in
the UI.

8. WINDOWS SETUP AND COMMANDS

Fresh setup from PowerShell at the repository root (Python 3.11+; Python 3.13
was used for the reported backend checks; Docker runner uses Python 3.11):

    py -3.11 -m venv backend\.venv
    .\backend\.venv\Scripts\python.exe -m pip install --upgrade pip
    .\backend\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
    if (-not (Test-Path backend\.env)) { Copy-Item backend\.env.example backend\.env }
    notepad backend\.env

Fill the blank MODEL_API_KEY (preferred) or META_API_KEY with a valid key in
the local ignored file; do not echo the value. Node 22.12+ is the documented
recommendation for Vite 8.3.5 (Node 24 was used for reported frontend checks).
Vite itself accepts Node 20.19+ or 22.12+. Install Node and Docker Desktop with
Linux containers, then check Docker Desktop/WSL and the daemon:

    node --version
    npm --version
    wsl --version
    docker version

    Set-Location backend
    .\venv\Scripts\python.exe -m uvicorn main:app --reload

setup above creates backend/.venv instead; for that environment from backend/,

9. DEMO SCENARIOS

Use the UI presets for the first three cases, select Generate, and inspect the
compact result summary plus Agent Logs, Generated Suite, and expandable raw
technical output:

1. Auth Route (Clean), preset "User Auth & Profile (Clean)": expect status
   success only after actual pytest collection and passing assertions. Check a
   positive collected/passed count, zero failures/errors, pytest exit 0, and
   the requested/returned model events.
2. Checkout (Defect), preset "Payment Checkout (Defect Detected)": the
   discount-factor defect should produce executed assertion failures and exit
   1. Defect classification is only valid with assertion evidence; the result
   should have failure_type assertion_failure and a Meta API_DEFECT review.
3. Invalid UserRegister: edit the clean source so UserRegister does not inherit
   BaseModel. Expect Application Initialization Error/application_error,
   FastAPIError, pytest exit 2, zero collected endpoint tests, zero failed
   assertions, one collection error, and no defect flag.
4. Self-healing: run the explicit live self-heal release check. It adds a
   missing fixture to a temporary copy after genuine model generation, expects
   a real test_setup_error and failing pytest exit, sends the failure through
   the normal Meta repair loop, then reruns the repaired suite in Docker. The
   report shows the real generation/repair model events, retry count, both
   pytest summaries, assertion-preservation check, and temporary-workspace
   cleanup. The source preset is not changed.

Normal backend/frontend tests use fakes and local deterministic checks; they
do not require Meta credentials, provider network access, or a Docker daemon.
The release verification command is separate and requires all three: live
credentials, network access to the configured provider, and Docker.
