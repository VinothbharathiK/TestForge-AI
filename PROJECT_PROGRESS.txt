TESTFORGE AI — PROJECT PROGRESS
As of: 29 October 2026

PROJECT SUMMARY
TestForge AI currently has a React/Vite user interface and an early FastAPI backend scaffold. The UI can send submitted FastAPI source to the local backend endpoint. The backend agent and Docker sandbox logic have been added, but the HTTP endpoint is still a dummy and does not call the agent. As a result, the current end-to-end flow does not yet generate or execute tests through the backend.

WHAT IS PRESENT

Backend files

backend/main.py
- Creates a FastAPI application.
- Enables CORS for all origins, methods, and headers.
- Defines a Pydantic request model with a single `code` string field.
- Exposes POST /generate-tests.
- The endpoint currently returns a fixed response containing "Backend connected!" and placeholder test code. It does not instantiate TestForgeAgent or use the submitted source.

backend/agent.py
- Creates an AsyncOpenAI client configured for https://api.meta.ai/v1.
- Requests model `muse-spark-1.1` and obtains META_API_KEY from the environment.
- Prompts the model to generate pytest code using FastAPI TestClient.
- Attempts up to three generate/run cycles and sends Docker failure output back to the model for repair.
- Returns status, defect_detected, logs, and code fields.
- Current repair prompt sends the error output but not the preceding test source, so the model does not receive the exact test it is asked to fix.
- After all attempts fail, the current code reports defect_detected=true even without confirming an API defect, and returns an empty code string. This can create a false defect report.
- If the model response content is null, code extraction can fail and be reported as an API error.

backend/sandbox.py
- Uses the Docker Python SDK and a temporary directory for main.py and test_app.py.
- Runs `python:3.11-slim`, installs pytest/FastAPI/httpx/Pydantic in the container, then runs pytest with short tracebacks.
- Mounts the temporary directory at /app in read-write mode and sets /app as the working directory.
- Moves the blocking Docker call to an executor so it does not directly block the async event loop.
- Requests automatic container removal and returns captured output for both pass and pytest failure cases.
- The container has no execution timeout or resource limits, has network access, and runs model-generated code with a read-write mount. The runtime pip install also requires network access. This is the current implementation and should be treated as a hackathon prototype rather than a hardened production sandbox.
- Docker client creation occurs in the sandbox constructor; if Docker is unavailable, agent construction will fail.

backend/requirements.txt
- Lists fastapi, uvicorn, openai, docker, pydantic, and pytest.
- Versions are not pinned.

Frontend

frontend/src/App.jsx
- React single-page interface with input, sample scenarios, status banners, activity logs, and generated-test display.
- Calls generateAndTestApi with the entered source.
- Uses defect_detected to choose between success and defect UI states.
- Also reads metrics and defectDetails, which the current backend response does not provide.

frontend/src/services/api.js
- Contains two sample FastAPI source presets.
- Sends the source as `{ code: ... }` to `http://localhost:8000/generate-tests` using Axios.
- Returns the backend response directly.

frontend/src/components/
- CodeInput.jsx: code entry, preset selection, and generation controls.
- AgentLogs.jsx: agent log/activity presentation and metric placeholders.
- TestViewer.jsx: generated test code and related output presentation.

Other frontend files
- `frontend/src/utils/testForgeEngine.js` contains a local analysis/test synthesis utility and `testForgeEngine.test.ts` contains its tests. The current API service no longer calls that local engine.
- `frontend/package.json` has Vite, React, Axios, Tailwind, TypeScript, and other frontend dependencies. Its dev script serves on port 3000.
- `frontend/vite.config.ts` configures React and Tailwind Vite plugins.
- `frontend/README.md` still describes the original AI Studio/Gemini setup, which does not match the current local FastAPI API-service flow.
- `frontend/.env.example` documents Gemini/Ai Studio variables; the current Axios service uses a hard-coded localhost backend URL instead.

KNOWN INTEGRATION GAPS
- POST /generate-tests still returns the original dummy response; the new agent and sandbox are not wired into it.
- The frontend expects optional metrics and defectDetails that are not returned by the current backend.
- App.jsx calls preset ids `auth_clean` and `checkout_defect`, while the current presets use `auth-clean` and `checkout-defect`; these quick preset buttons will not find their presets.
- The backend CORS policy is permissive. This is convenient for local development but should be narrowed for deployment.
- The frontend dev server is configured for port 3000. The backend service URL is localhost:8000.
- The current project README/setup instructions still need to be reconciled with the active backend architecture.

LOCAL WORKING TREE NOTES
- Modified tracked files currently include backend/agent.py, backend/sandbox.py, frontend/package.json, and frontend/src/services/api.js.
- An untracked backend/.env file exists locally. Its contents were not read for this report; keep credentials out of source control.
- An untracked backend/__pycache__/ directory exists locally and is generated Python cache data.
- The frontend package change adds/reorders @types/express; the package entry is present in the dependency list.

NEXT STEPS TO MAKE THE APP END-TO-END
1. Wire POST /generate-tests to create/use TestForgeAgent and pass CodePayload.code into generate_and_heal.
2. Decide and align the response contract for success, confirmed defect, exhausted retries, and operational errors. Include metrics/defectDetails only if the UI needs them.
3. Pass the failed test source into each repair prompt and do not mark every exhausted retry as a confirmed API defect.
4. Add a hard Docker execution timeout, resource limits, and stronger isolation. Review whether tests really need network access or a read-write source mount.
5. Align the preset identifiers in App.jsx and api.js.
6. Update README/setup instructions for META_API_KEY, Docker availability, backend startup, and frontend startup.
7. Add backend tests for the endpoint, agent retry behavior, and sandbox result handling; then verify the full local flow.

COMPLETED: TESTFORGE AI BASELINE MVP
Date: 29 October 2026

All four development milestones are complete and committed on the master branch (commits
f0d5e7a through 992da5c). The application is a demo-ready MVP.

What is implemented and verified:

- React/Vite frontend and FastAPI backend, fully wired end-to-end.
- Real Meta Muse Spark 1.3 integration via the OpenAI-compatible AsyncOpenAI SDK.
- Docker-isolated pytest execution with resource limits (512 MiB memory, 1 CPU, 64
  processes, 60-second timeout, 64 MiB noexec tmpfs) and full cleanup on completion,
  timeout, error, and cancellation.
- Evidence-based classification of passing tests, genuine API assertion failures,
  application initialization errors, test collection errors, and test setup errors.
  Classification requires real pytest evidence; it does not infer outcomes from absence
  of evidence.
- Autonomous self-healing with a maximum of three repair attempts. The agent repairs
  test-harness failures only; it does not remove or weaken assertions to force a
  defective application to pass.
- Live repair and Docker rerun verified with a real missing-fixture injection: original
  assertions were fully preserved in the repaired suite.
- Responsive interface with result summaries, execution logs, and a generated test
  viewer. Layout uses fluid CSS component classes (tf-content-shell, tf-workbench-panel)
  and normalised typography.
- Explicit CORS policy, input size limits (256 KiB source, 512 KiB tests), and
  documented credential handling via backend/.env.
